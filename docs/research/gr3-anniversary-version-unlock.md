# GR III 纪念版服务固件的版本准入适配

本模块省略配置时关闭。开启的常规模式为 `dsp-package-only`：只提高 DSP 包版本至同一 `2.10` 公共线的上限 `2.10.255.255`，保留整个 CPU 载荷及其外层版本。这个上限是包头策略，**不是已知的纪念版版本，也不是机身实际运行版本**。CPU 较高时原厂比较仍会拒绝，不能承诺所有纪念版机身都能刷写。高级 `observed-versions` 模式仍要求机身实际的完整 DSP、CPU 四段版本；公开显示的“2.10”不足以替代该读数。本项目尚未取得并验证 20 周年服务固件的代码及完整版本。

## 原厂 ARM 证据

以下地址针对公共 GR III 2.10 RTOS，SHA-256 为 `8a4eafcad2716e0b21e9909264e1242e534f0e39e05cba82a53546ceb4070b67`。

- 更新状态 `53838cd0` 调用 `536284e0`，`53838cd4/8` 检查返回值并进入失败分支。
- `53628524..54` 按更新对象 `+2c` 分派，不能将它等同于可随意更改的固件分区编号。
- 类型 0/1：`536298f8` 读取候选外层 `+38..3b`，组成大端版本；`53628628/2c` 的 `CMP/BLO` 拒绝严格较低值。
- 类型 2/3/4：`5362a864` 经 `5362bc10`、`5362bc34` 分别读取外层 `+38`、`+50`。第一项在 `536285d4/8` 与当前 DSP 比较；第一项不低后，第二项在 `53628640/44` 与当前 CPU 比较。两项均须不低于机身当前对应值。
- 类型 6：`53629008` 读取 CPU 载荷 `+90..93`，`53628574/78` 拒绝低于当前 CPU 的版本。
- 当前 DSP 取自 `53547bac → 53550d98`，当前 CPU 取自 `53547bf0 → 53550da4`。官方 `CameraLogController` 的 `5319d3dc..418` 将前者明确标为 `DSP Version:`，`5319d420..45c` 将后者标为 `CPU Version:`，经 `5319d254` 输出四段十进制。因此**外层 +38 是 DSP，外层 +50 是 CPU**。早期报告对这两个名称的标注相反；基线两个数值均相同，旧探针未暴露该名称问题。
- CPU 校验包装 `536290c8` 先验证 CPU 载荷 `+80` 项目编号及两个标记，再在 `536291bc` 转到 `53629044`。后者对 128 KiB CPU 载荷逐个大端 32 位字加和。更改 `+90` 后必须修复 `+7c` 补数。

`tests/test_gr3_updater_version_gate.py` 从仓库精确官方 BIN 自行解码，执行未修改的原厂 gate/parser。20 个逐组件高于、等于、低于组合确认上述分支；另有 4 个常规模式对照验证 DSP 上限通过时，类型 2/6 仍在机身 CPU 较高时拒绝。这些 gate 测试仅替代当前版本 getter 及日志输出。另有 4 个 CPU 包装测试：官方通过、仅改版本失败、修复 CPU 补数通过、项目编号不同拒绝。新增 2 个 DSP 启动/模型报号对照，执行真实 getter、setter、模型切换和 memcpy，见下文。这些测试不执行闪存写入、完整更新状态机或机身硬件。

在待刷 RTOS 内改 `BLO`，无法改变安装前正在机身上运行的服务固件门禁。本模块不修改比较指令，不利用类型 5 的局部成功路径，也不写入 `ffffffff` CPU 校验哨兵。

## 常规模式只适配 DSP 包版本

```js
normalizeVersionUnlock(); // {enabled:false}
normalizeVersionUnlock({enabled:true, mode:'dsp-package-only'});
// {enabled:true, mode:'dsp-package-only'}
```

此模式不接受 `dsp/cpu` 读数字段，也不猜测当前 CPU 版本。仅将外层 `+38` 与 RTOS 载荷 `+2038` 设为 `020affff`，修复 decoded 与外层校验；外层 CPU `+50`、CPU 载荷 `+90`、CPU 补数 `+7c` 以及整个 CPU 分区全部逐字节保持原样。

公共 DSP 启动报号来自代码常量，所以下次启动的这条公共版本 getter 仍返回 `2.10.21.27`，不会因为本模式的 DSP 包头上限而变为 `.255.255`。此结论仅覆盖下文已追踪的公共运行报号及更新 gate；不等于已经验证未知服务更新器、引导程序或完整恢复流程。CPU 门禁不变：若服务 CPU 高于公共 `2.10.21.27`，仍会拒绝候选，不能把该模式宣传为绕过所有版本限制。

## 高级模式分别匹配实测组件版本

```js
normalizeVersionUnlock({enabled:true, dsp:'02.10.21.40', cpu:'2.10.21.27'});
// {enabled:true, dsp:'2.10.21.40', cpu:'2.10.21.27'}
// 也可显式传 mode:'observed-versions'；旧调用契约保持兼容。
```

`dsp/cpu` 是机身当前读数，不是用户任意指定的目标。DSP、CPU 均须为同一 `2.10` 公共版本线；四段各为 0–255 的十进制数，版本比较采用原厂所用的大端无符号 32 位值。目标分别为 `max(公共基线 2.10.21.27, 对应机身当前版本)`，相等值通过已经执行验证的局部比较。

上面的 `2.10.21.40` 是测试用合成值，**并非已经确认的纪念版版本**。例如这个合成输入只要求 DSP 为 `.40`，CPU 仍为 `.27`，并不需要将 CPU 也提升到 `.40`。

版本副本保持对应关系：

| 组件 | 外层版本 | 内部版本 |
| --- | --- | --- |
| DSP | `+38` | RTOS 载荷 `+2038` |
| CPU | `+50` | CPU 载荷 `+90` |

## 调用与独立审计

```js
const option = normalizeVersionUnlock(input);
// before 必须先通过 native/composition 的原有独立审计。
const {candidate, receipt} = applyVersionUnlock(before, option);
const independentlyRead = verifyVersionUnlock(before, candidate, option);
```

模块接受已经完成 native/composition 的候选，允许既有 RTOS 扩容和其他已审计内容；不对该候选调用要求精确官方 SHA 的 `inspectOfficial`。这不代替前置内容审计。

开启后检查 GR III 项目编号 588、项目标记 `024c024c`、容器类型、14 个分区的名称/标志/长度、三个加和及输入四个基线版本副本。独立 verifier 重新解码前后数据；常规模式只允许两个 DSP 版本字段与 decoded、外层两个校验字变化，并单独断言整个 CPU 分区相等；高级模式只允许四个版本字段与 CPU、decoded、外层三个校验字变化。只有帧内容及此前 8191 字节回溯窗口均未变化时才复用压缩帧，否则改为 literal，避免历史引用读到新版本字节。帧重封装所需的外层 encoded 长度另行允许；decoded 长度、分区头、机型、引导程序、更新器代码和其余所有 decoded 字节须与前置候选相等。

关闭时返回逐字节相同的副本，独立 verifier 拒绝任何差异。开启但机身两个版本均不高于公共基线时也保持容器原字节。

receipt 记录前后 SHA、模式、目标 DSP/CPU 包版本、四处回读结果、加和与差异白名单检查，并明确 `camera_verified:false`。常规模式的 `current_versions:null` 明确没有取得机身读数，`target_versions.cpu` 是保留的公共载荷版本，不是机身当前 CPU；高级模式才记录实际输入读数。模块不提供刷写、机型绕过或引导程序绕过。

## 仍需机身确认的范围

本策略只处理已经证实的严格低版本比较。公共固件中的比较行为，不代表服务固件的更新器字节必然相同；其余准入条件、周年专属资源、服务 CPU/DSP 代码兼容性、整条刷写及恢复路径均未由此证明。提高公共代码的元数据版本不会把它变成服务固件代码；高级模式提高 CPU 尾号时，还可能使原始公共包随后因 CPU 版本较低被拒绝。常规模式不提高已定位的 DSP 运行报号、保留全部 CPU，但仍不能据此宣称完整恢复路径已验证。不得把本离线 receipt 写成“20 周年机身已支持”或“已具备恢复能力”。

## 无需先安装候选的版本取证

原始 GR III JPEG/DNG 的 RICOH MakerNote `0x27` 保存 DSP 版本，四个字节分别 XOR `ff` 后得到四段十进制数。本机 `00004105.JPG`、`00004106.JPG` 均为 `fd f5 ea e4 → 2.10.21.27`，与既有样本的 ExifTool 结果一致。这可用于服务固件机身直接新拍原图后读取 DSP，不能从聊天软件重存图或“2.10”显示推断尾号。[ExifTool 官方 Pentax.pm](https://raw.githubusercontent.com/exiftool/exiftool/master/lib/Image/ExifTool/Pentax.pm) 的 `pentaxFirmwareID` 与 `0x27/0x28` 给出此解析。

`0x28` 对应 CPU，但目前本机 GR III 原图没有该标签，既有 EXIF 清单也没有 `CPUFirmwareVersion`。不能用 DSP 读数替代 CPU。已定位 CameraLogController 为工厂 screen ID `01000007`（`5316f450..45c → 53170480 → 5319d330`），它能显示两个完整版本；尚未证明无需更改固件即可进入该诊断页或导出的用户操作路径。现有 M10V SD 日志没有写入这两个完整版本。

高级模式仍要求两个实际读数；缺 CPU 时不能使用高级模式。常规模式保留未知 CPU 的原厂门禁，下面的公共固件版本源证据不能推导未知服务固件的 CPU 实际版本。

## DSP 运行报号与 RTOS 版本字段分离

公共 RTOS 启动初始化有一条明确的代码常量路径：

- `53560350 → 5381fe6c` 返回立即数 `020a`；`5356035c → 5381fe84` 返回立即数 `151b`。
- `53560360` 将前者左移 16 位加后者，`53560368` 把 `020a151b` 写入栈结构 `fp-74`。
- `5356042c/34` 从 `fp-7c` 传入此结构，所以 DSP 是该结构的 `+8`。`5354b654` 提交属性 0；属性表 `54093030` 的处理器 `5353eda4` 调用 `53551f74`，后者把结构的 `51` 字节复制进系统版本模型。当前 DSP getter `53550d98` 读取模型 `+8`。

这条初始化链没有读取 RTOS `+2038`。另有四段显示所用的代码 getter `5381fe74/7c/8c/94`，分别返回 `2/10/21/27`。

用 Unicorn 执行未修改的 `5356034c..53560368` 及上述两个真实 getter，以 `5356036c` 为初始化片段停止点：将载入镜像的 `53002038` 分别设为 `02 0a 15 1b` 和合成测试值 `02 0a 15 28`，两次都得到栈内 DSP 字段 `020a151b`。随后把对照扩大到 `02 0a ff ff`，将该栈结构送进真实模型 setter `53551f74`，执行 `5355198c` 模型切换和原厂 NEON memcpy `5313fd80`，最后调用真实 getter `53550d98`；公共头与提高后的头都报 `020a151b`，没有替代这些函数。该测试启用了 Unicorn 的 VFP/NEON 支持。这是启动片段、模型 setter/getter 的 ARM 执行对照，没有执行完整启动、模型消息队列或机身硬件。因此可以确认这一条运行 DSP 报号路径来自代码常量，不能据此声称所有启动器及包头副本均可任意省略。

## CPU 载荷头确实在写入范围内

CPU 载荷 SHA-256 为 `86745d31ec43427b56054a37bd9d47a5b60791829886da39833224cd4aa67290`，大小 `20000` 十六进制字节。它是 Renesas RX 指令集，复位映射基址为 `fffe0000`，不能用 ARM 反汇编解释。

本轮使用 [GNU binutils 的 RX decoder](https://raw.githubusercontent.com/RTEMS/sourceware-mirror-binutils-gdb/master/opcodes/rx-decode.c) 及配套 [opcode/rx.h](https://raw.githubusercontent.com/RTEMS/sourceware-mirror-binutils-gdb/master/include/opcode/rx.h) 只读解码；取得的源码 SHA-256 分别为 `b91eccac0169ccf82fcb03ac218730fa23bcd476eae211ab26db9ffba4ddf24d`、`d71efde07b79636f6dce40b024dc4788221e2418618428dbabcb026ef11deeec`。下面地址均是该 CPU 镜像的 RX 地址，不是 RTOS ARM 地址。

- ARM 发送侧 `53629394..3d0` 以从 0 开始的块号乘 `400`，直接从 CPU 载荷基址加该偏移发送每个 `400` 字节块。第一块包含头部，没有加 `100`。
- RX 接收侧 `fffe9c53` 的状态在 `fffe9c67..98` 将块号与目标偏移初始化为 0；`fffe9cc9..9ce8` 接收完整 `400` 字节至 RAM `7800`。
- `fffe9d46..53` 计算范围 `fffe0000+offset .. fffe03ff+offset`；`fffe9d5a` 调用范围擦除设置，`fffe9d6e` 调用编程范围设置。
- `fffe9d7e..8a` 把源 `7800`、上述目标、长度 `400` 传给 `fffe9b12`。该函数将长度右移 2，逐个取源 32 位字，经 FCU 数据/命令寄存器提交，并每次将源、目标各加 4。`fffe9d96` 才把下一块偏移加 `400`。

因此现有代码证据排除了“CPU 真正写入时统一跳过前 `100` 字节”的解释。这里仅静态追踪了收包、目标地址和 FCU 编程循环；没有执行芯片闪存控制器或真实刷写，也没有假定未知服务 CPU 固件的接收程序一定相同。

## CPU 运行回复会读取头部尾号

RX 命令表的镜像偏移 `454` 是命令 `4e`，`458` 的处理器指针为 `fffe401b`。该处理器把两个版本字写入回复缓冲区 RAM `a28+2/+4`：

- `fffe401d → fffe5121`：从实际闪存 `fffe0091` 读取一个字节，再置位 bit 9，组成 `02xx`。
- `fffe402e → fffe512b`：从 `fffe0093` 读取一个字节，再 OR `1500`，组成 `15xx`。
- `fffe4021..2c`、`fffe403b..46` 将这两个字各拆成高、低字节写入回复。公共版本 `02 0a 15 1b` 得到 `020a/151b`。

ARM 通信命令表 `53d1cd28` 对应同一个 `4e`；接收端 `53572480..c0` 从回复取两个字并组成 `(word0 << 16) + word1`，经 `5354b714` 提交 CPU 属性 4；其表项 `54093050 → 5353f224 → 535529a0` 更新模型 `+c`，与当前 CPU getter `53550da4` 一致。这条跨 CPU 通信链已做静态追踪，尚未做真实串行协议/整机执行。

应精确区分：这条回复路径的第一段 `2` 和第三段 `21` 是 RX 代码常量，第二段和第四段来自头部 `91/93`；不能笼统声称四个字段都直接从 `90` 原样加载。但在常见的 `2.10.21.N` 情形，修改 `93` 的尾号会改变下次启动的 CPU 运行报号。因此“包声明提高、CPU 运行号仍保持公共尾号”在这条已定位的公共 CPU 路径上不成立。提高 CPU 尾号后，原始公共包可能被当前版本比较拒绝，低版本恢复不能宣称无影响。

结论是 DSP 运行源已有代码常量证据，CPU 尾号则有头部读取及包含头部的写入范围证据。因此常规模式只提高 DSP 的两个包字段，保留全部 CPU 字节并接受原厂 CPU 门禁可能拒绝的结果；高级模式仅在实际取得两个完整读数后提供。模块不猜测未知服务 CPU 的尾号，也不提供“只提高 CPU 包声明而不影响 CPU 运行报号”的保证。
