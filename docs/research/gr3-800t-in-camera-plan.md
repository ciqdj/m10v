# GR III 800T 机内 JPEG 红晕：实现门槛与当前证据

目标限定为拍摄保存的 JPEG；DNG/RAW 不改，取景预览和机内 RAW 再显影不在首版范围。浏览器现有红晕算法只是视觉参考，不能直接写入固件。此页只针对已提供的 GR III Street Edition 2.10 官方与修改包。

2026-10-12 的样本和原厂 ARM 继续分析见 [EXIF 与色度描述符记录](gr3-800t-samples-2026-10-12.md)。新增证据将调用点定位到 `JpegEncodeMacroProcess`，确认所观察的描述符创建路径使用亮度区和合并色度区，14 项独立 CPU 探查通过；Cb/Cr 字节顺序和全部 RAW/JPEG 分流仍未证明。用户选择同时提供实拍4、实拍5参考的两种强度。DNG 内含全尺寸 JPEG 预览，后续“RAW 不变”验收需区分 CFA 像素与预览。

用户已确认测试机目前运行其提供的修改固件，柯达、250D 等现有滤镜可以正常使用。这是**用户报告的实机运行结果**，说明该机身接受并运行过修改固件；尚无机内读回哈希，不能把它等同于本地 `fwdc239b-modify.bin` 的逐字节验证，也不能推断新增 800T 代码安全。

CineStill 对其胶片特征的说明指出，强高光的反射会在红敏感层形成红色光晕，点光源与较暗背景最容易显现。因此验收图应包括夜景点灯、白色标牌、湿地反光及无强光的对照画面，不能只用调色 LUT 的色差评分：[CineStill 官方 FAQ](https://cinestillfilm.com/pages/frequently-asked-questions)。

## 已复核的固件锚点

运行 `node scripts/analyze_gr3_800t_hook.mjs` 会对两个输入包重新算完整 SHA-256，并独立解码修改包。检查结果：

| 项目 | 精确结果 | 能说明什么 |
| --- | --- | --- |
| 官方 RTOS 捕获调用 | `0x535048E8: 0E 9D 06 EB` → `0x536ABD28` | 已找到参考实现所使用的原始 ARM `BL` 调用点 |
| 已有修改包同一调用 | `0x535048E8: 9F D2 2E EB` → `0x540B936C` | 时间戳等已有功能占用了同一适配器链；新功能必须合并，不能覆盖原跳转 |
| 已有修改包适配器 | `0x540B936C` 保存寄存器和状态位，`0x540B9380` 调用 `0x540BA254`，`0x540B9394` 间接跳回 `0x536ABD28` | 已确认时间戳处理之后仍执行原厂被调函数；尚未证明它拿到 JPEG 色度平面 |
| 已有程序分支 | 程序偏移 `0x3380` 为 `B3 03 00 EB` | 与缓存 GRLife 时间戳模板预期相符 |
| 已有程序后半页 | 程序偏移 `0x5000..0x5FFF` 为零 | 有可研究的物理字节范围；尚不等于可安全执行的代码空间 |
| GR III 与 GR IIIx 参考 RTOS | 替换锁定的机型身份字节后，完整 RTOS SHA-256 为 `0f11b0d28bc67932d044c5d01bc0314844a756057c89984278c73a23449a24c6` | 两者在该参考构建基础上字节等价；不证明相机运行行为等价 |

缓存的 GRLife `urban160-film-texture.json` 含一个离线验证的 JPEG 高光**亮度**扩散程序。它依赖这个捕获调用、会改写亮度平面，但既没有红色独立通道，也没有 GR III 2.10 的实机验收。其证据文件及 C 源码未随本地缓存提供，不能把模板里的 `verified_offline` 当成我们自己的动态证明。缓存说明还记录 GR IIIx 颗粒测试首次刷入后拍摄死机、重刷后恢复；故不采用“先刷柔光，再看效果”作为默认实验。

参考 blob 的 ARM 反汇编给出更窄的结构线索：假定按模板地址 `0x540BB000` 放置，`0x540BB02C` 从上下文 `+0x3C` 取描述符，`0x540BB0CC..0x540BB0D8` 从该描述符 `+0x10/+0x12/+0x14/+0x04` 分别读取 16 位宽、高、步幅与数据指针。这是**参考程序的读取行为**，只足以定位一个字节平面；未证明另两个色度平面的位置，也未证明该格式在全部 JPEG 尺寸、色彩模式和 RAW+JPEG 设置下稳定。

已有修改包的时间戳处理例程也读取上下文 `+0x3C`，并检查描述符 `+0x04/+0x08/+0x10/+0x12/+0x14`。其中 `+0x04/+0x08` 被用于地址与跨度检查，不能在没有更多证据时把第二个值当成 Cb/Cr 平面指针。两个参考例程都说明此处存在可访问的图像描述符，但仍不足以证明红晕所需的色度布局。

上述段落记录初始参考例程的证据边界。继续追踪原厂 `CalcYCbCrAddress`、描述符创建者和缓存消费者后，`+0x08` 已被定位为本次创建路径中的合并色度区，`+0x0C` 写为零；低级格式 1/2 分别对应 4:2:2/4:2:0。尚不能将该合并区按 UV 或 VU 顺序写入，也未证明所有拍摄配置均走这一创建路径。

## 800T 原生算法方向

1. **先追数据布局**：从 `0x535048E8` 的被调函数与适配器继续追踪描述符，静态确认 JPEG 主图的亮度和色度平面、尺寸、步幅、采样格式、生命周期以及 RAW/DNG 分流条件。不能用主机端 `RGBA` 布局猜相机内存。
2. **再做颜色内核**：在 JPEG 所用亮度平面提取强高光掩码，缩小到色度采样网格后作有界扩散；仅在周边暗像素增加红向色度，亮点中心及 DNG 数据保持不变。半径按输出像素尺寸缩放，处理时间、临时内存和越界检查要有明确上限。若相机实际使用别的像素格式，按已证实格式重写此步骤。
3. **合并已有捕获链**：使用单一入口调用原始处理和时间戳适配器。每个覆盖的 ARM 指令必须有精确原字节、指令边界、分支距离、寄存器/栈约定和缓存刷新证明。不能直接把 GR IIIx 的亮度扩散 blob 改成红色，或覆盖现有时间戳 `BL`。
4. **离线构建与回读**：固定官方包身份、改动白名单、分区容量和重定位范围；构建后用独立解码器回读程序、所有分区、版本、校验和与非目标字节。失败时只出报告，不出 BIN。现有浏览器参数 JSON 不进入固件构建器。
5. **实机验收**：用户已确认测试机是 Street Edition 2.10，正运行其提供的修改固件，并保存了官方包。先记录**现有修改固件**的基线照片和更新界面可进入性；候选包完成离线证明后，才进行单功能、单机身实验。记录更新界面每个阶段、启动、JPEG-only 和 RAW+JPEG 拍摄、照片保存时间、夜间点光源前后对比以及 DNG 原始数据。任何卡死、异常保存或更新拒绝都终止本轮，不叠加其它功能。

## 当前阻断项

- **色度字节顺序与 JPEG 专属性未证明**：`0x535048E8` 已定位为 JPEG 编码宏处理对象内的调用，描述符的合并色度区已获得静态与独立 CPU 证据；仍不能称为已验证的红晕挂钩。
- **相机适配器未完成**：两档 C/ARM 红晕内核已实现并在显式软件 ABI 下验证；真实相机色度编码、原厂分配/缓存适配和相机时间预算仍未验证。详见 [实施验证记录](../testing/gr3-800t.md)。
- **没有 800T 候选包**：字节级测试只针对已有官方/修改包；没有为 800T 生成或导出任何 BIN。
- **实机恢复未知**：用户保存的官方 BIN 只可能在相机还能进入更新界面并接受该包时用于重刷；当前没有验证同版本重刷或无法开机后的恢复方式。不能把“有官方包”标成“已具备硬件恢复”。

## 现在可做的无刷机基线

1. 在相机菜单拍照记录机型与固件版本。把保存的官方包交给本工作台核对完整 SHA-256；文件名或显示版本相同不足以确认内容相同。
2. 依理光的官方步骤，用相机格式化的 SD 卡放置官方 `fwdc239b.bin`，满电、关机、按住 Menu 开机，**只确认能否显示更新界面，不选择 Execute**。记录屏幕提示后正常退出。这样只能证明当前相机能进入更新界面，不能证明同版本重刷可行。
3. 在**当前已运行的修改固件**上固定夜景点光源、曝光、白平衡、焦距与机位，分别拍 JPEG-only 和 RAW+JPEG；再拍一张没有强高光的对照。记录所选胶片滤镜。保留相机写出的原始 JPEG/DNG，不经手机应用或修图软件重存，并记录每次从按快门到可回看的时间。
4. 这些照片用于建立红晕强度、色彩与保存时间的对照；它们无法替代固件内存布局证明。取得色度格式和 JPEG-only 路径证据之前，不发布可刷写的 800T 包。

理光官方支持页列出 GR III Street Edition 属于 2.10 适用机型，并要求 SD 卡根目录放置 `fwdc239b.bin`、满电、关机后按住 Menu 开机进入更新流程；该流程是官方固件说明，不证明自定义包可被接受或可在故障后恢复：[RICOH GR III 固件支持页](https://www.ricoh-imaging.co.jp/english/support/digital/gr3_s.html)。
