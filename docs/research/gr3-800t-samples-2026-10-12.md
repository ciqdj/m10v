## DNG 的三层图像

每个 DNG 都包含以下三类数据：

1. 主传感器数据位于 SubIFD：6112×4064、14 位 RGGB CFA，默认裁切 6000×4000，使用 JPEG 压缩的 CFA 数据。这里 `Compression=JPEG` 不代表它已变为彩色成品 JPEG。
2. SubIFD1 内的全尺寸 JPEG 预览：6000×4000、8 位 YCbCr 4:2:2；约 2.79–2.98 MB。
3. IFD0 的 160×120 RGB 缩略图，另有 MakerNote 的 720×480 JPEG 预览。

本次按 EXIF 的偏移和长度直接读取 SubIFD1 预览，用 Pillow 解码后与同拍 JPEG 比较。6 组均有轻微像素差异，平均绝对差为 0.52–1.59/255，最大通道差为 11–37/255；**不声称逐字节或逐像素相等**。差异来源本次未定位，不能用这些数字证明任一文件经过重存。

800T 的“RAW 保持不变”应明确指 CFA 像素及其必要解释参数。DNG 内的彩色预览是否同时带红晕，需要单独验收；整份 DNG 的哈希也会随时间、元数据和预览改变。不同按快门的 DNG 不能用哈希相等判断算法是否污染 RAW。

黑电平并非固定值：本批样本为 256、512 或 1024；白电平为 14323、14328、15352 或 15870。制作 RAW 渲染参照必须逐张应用黑白电平和 AsShotNeutral，不能统一套用一个常数。

所有 12 个 GR III 文件的 MakerNote `ColorMatrixA2`、`ColorMatrixB2` 相同。`SaturationInfo` 的 598 字节与未解释的 0x021a 标签的 2048 字节，在全部文件中也分别相同；没有可导出的 `ToneCurves` 标签。故这些记录不能直接给出各自定义胶片的完整 LUT。DNG 还有 73740 字节的未知 0x0405 数据，本次只提取，尚未解码其结构。

## 新增的原厂 ARM 证据

仅适用于官方包 `d6a3c9c288d784080e7b283222ecdd8752adfeed6faa36dab44f73115354bfd4`，其 RTOS 为 `8a4eafcad2716e0b21e9909264e1242e534f0e39e05cba82a53546ceb4070b67`。

### 调用点所属对象

`0x535047D4` 函数通过 r4 保存消息 `r1+8` 中的上下文；在 `0x535048E8` 调用原厂 `0x536ABD28`。其 vtable `0x53C62A08..0x53C62A18` 包含该函数，类型信息 `0x53C62A50` 的名称指针指向 `0x53C62A5C`，字符串为 `22JpegEncodeMacroProcess`。初始化函数 `0x535049D4` 同时采用 `JpegEncodeMacroProcess` 调试名。

这将调用点定位到 JPEG 编码宏处理对象，比笼统称为捕获函数更精确。但尚未穷举该对象的全部调用者，不能据此断言只用于按快门后的独立 JPEG，也不能排除 DNG 预览或机内 RAW 再显影。

### 图像描述符不是三个独立色彩平面

原厂 `0x534A2CF0` 从高级图像对象建立低级描述符；`0x536A3D84` 按字段复制描述符：

| 低级描述符字段 | 当前证据 |
| --- | --- |
| +0x00，u8 | 格式：原厂断言标明 1=4:2:2、2=4:2:0 |
| +0x04，u32 | 第一数据地址，柔光代码处理的亮度区 |
| +0x08，u32 | 第二数据地址；原厂地址计算器产生紧接亮度区的色度区起点 |
| +0x0c，u32 | 第三地址字段；本次观察的原厂创建路径写入 0 |
| +0x10/+0x12，u16 | 图像宽/高 |
| +0x14/+0x16，u16 | 分配宽/高，用于原厂缓存跨度计算 |
| +0x18/+0x1a，u16 | 位置偏移字段，观察的完整图创建路径写入 0 |
| +0x1c，u8 | 观察的创建路径写入 2；语义尚未完整追踪 |

`0x5350401C` 的原厂格式断言绑定字符串 `srcInfo->GetFormat() == ImageProcessCommonItem::YCbCrFormat_422`，并检查格式值 1；目标 420 的断言检查值 2。`0x534A276C` 将高级枚举 3/4 转换为低级枚举 1/2，`0x534A27D8` 反向转换。

`CalcYCbCrAddress`（`0x534A2AC4`）对高级枚举 3/4 返回 `{base, base + allocated_width * allocated_height, 0}`，要求起点与色度起点满足 16 字节对齐。`0x534AB1A4` 缓存处理对低级格式 1 处理同样大小的两区，对格式 2 的第二区处理半个大小。结合 4:2:2 的像素数，这是**合并色度区**的有力证据，不能将 +0x08/+0x0c 直接命名为独立 Cb/Cr 平面。

### 独立 CPU 探查

本地临时脚本 `probe-descriptor.py` 使用 Unicorn 执行上述原厂 ARM 字节，没有使用 GRLife 算法结果代替执行。对 6 个尺寸、2 个格式共 12 个地址计算用例，另有 2 个缓存跨度用例，合计 **14 项通过**。包括 6000×4000 和 6016×4000 的跨度差异，确认算法不能只以可见宽度代替分配宽度。

格式转换、地址计算、原厂对齐断言及分支真实执行；缓存管理器调用被拦截记录，CP15、ISP、JPEG 硬件及真实相机内存没有仿真。临时脚本依赖本机提取的 RTOS 路径，仅作为本次分析探针，不是生产验证器。

### 缓存维护已缩小到原厂函数链

柔光引用的 `0x5383C8A8` 设置地址范围操作和类型 2，调用 `0x5383C728`；后者的类型 2 范围分支经 `0x53853040` 到 `0x53000930`，逐 64 字节执行 `MCR p15,0,...,c7,c14,1`，结尾 `DSB`。这是原厂 clean+invalidate 范围路径的静态指令证据。新内核仍需按实际亮度、色度跨度维护缓存并证明调用前后的所有权；函数地址已找到不等于硬件执行时序已经验证。

## 对实现的直接影响与剩余工作

1. 800T 至少需要色彩基底与空间红晕两部分；原厂颗粒可作为独立可选项。复制亮度柔光 blob 不能产生目标橙红外溢。
2. 暂按半平面 4:2:2 描述符追踪，继续核实合并色度区的 Cb/Cr 顺序、数值编码以及硬件读取配置。**本次没有证明 UV/VU 顺序或无符号 128 中心编码，不允许猜测后写入。**
3. 需追踪 `JpegEncodeMacroProcess` 的配置创建者和全部分流；DNG 预览是否复用主图与 RAW 写出路径必须分开证明。
4. 在已确认格式上做弱/强两档红晕内核、边界与时间预算测试，然后合并现有时间戳调用链；现有修改包占用了同一入口。
5. 通过独立构建回读后再给出实验固件。本次交付的是样本分析与新增原厂证据，尚无 800T ARM 内核或可刷入候选。
