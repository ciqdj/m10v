# m10v 多机型固件编辑平台设计

状态：2026-10-11 已经用户审阅确认；实施路线见 `docs/superpowers/plans/2026-10-11-m10v-multimodel-roadmap.md`。

## 1. 目标

把当前只针对 GR III 的本地工作台改造成可扩展的理光 GR 系列固件编辑平台。第一期完整支持 GR III 与 GR IV，未来可增加 GR II，但不得在没有固件证据时预填 GR II 的地址、版本或校验规则。

平台复刻 `gr-custom-tool` 公开版已经实现的产品能力：自定义裁切比例、关机图案、编辑草稿、编辑备份、固件构建、构建清单、版本历史、重新载入、回退固件以及 LLVM 工具链配置。参考项目中仍标记为“开发中”的滤镜不属于本期范围。

平台只生成文件，不自动向相机写入。离线构建成功表示成品通过了适配器实现的静态检查，不表示相机已经接受、启动或正确运行。

## 2. 核心原则

1. **机型规则隔离。** GR III 与 GR IV 不共享固件偏移、机器码、版本分配或校验假设。
2. **内容识别优先。** 文件名和公开版本号不能决定兼容性；必须通过完整文件哈希、容器结构、分区布局和适配器证据识别。
3. **输入不可变。** 官方输入保存为只读对象，所有构建从已验证输入或可恢复到官方基线的兼容候选重新生成。
4. **独立回读。** 构建器与验证器分离；成品必须重新打开、解码并验证功能状态和非目标差异。
5. **状态不夸大。** `offline_verified`、`reference_verified` 与 `hardware_verified` 是不同状态。
6. **原子输出。** 构建失败、验证失败或进程中断不得留下可下载的半成品固件。
7. **GPL 一致。** 平台继续采用 GPL-2.0-only，并保留 `gr-custom-tool` 派生代码的来源与修改说明。

## 3. 总体架构

平台由四层组成：

```text
Web UI
  ↓
本地 Node 服务与共享领域层
  ↓
统一适配器协议
  ├── GR III Node 适配器
  ├── GR IV Python 适配器桥接 gr-custom-tool
  └── GR II 空注册位
  ↓
不可变对象库、项目草稿、构建与历史存储
```

Node 服务继续只绑定回环地址，并对所有改变状态的请求执行会话令牌、同源、大小限制和路径边界检查。Web UI 只消费统一领域对象，不包含固件地址、机型分支或版本计算。

GR III 适配器沿用当前已验证的 Node 容器解析、帧重放和独立验证代码。GR IV 第一阶段保留 Python 3.12 实现，以一个窄 JSON 协议桥接现有 `gr-custom-tool` 核心，避免把大量已测试的 ARM 编译、裁切注册表和关机菜单逻辑重新翻译后失真。适配器协议只传递受控 JSON 和已验证的本地临时文件路径，不通过标准输出传输固件字节。

## 4. 统一适配器协议

每个机型适配器必须实现以下语义；具体语言不影响平台调用：

- `detect(input)`：只读探测，返回明确匹配、不匹配或损坏；多个适配器同时匹配时整体拒绝。
- `inspect(input)`：返回机型、内部/公开版本、容器、分区、输入身份和证据等级。
- `capabilities(project)`：逐项声明裁切、关机图案、构建、历史与回退能力及阻断原因。
- `createDraft(input)`：从固件真实内容读取原厂裁切、资源和可编辑状态。
- `validateDraft(draft)`：拒绝未知字段、越界数量、重复身份和与机型不符的数据。
- `previewCrop(request)`：只计算并返回该适配器认可的几何预览。
- `prepareShutdownAsset(request)`：规范化图片、生成预览并验证目标编码边界。
- `build(input, draft, options, outputStage)`：只向平台提供的隔离暂存目录写入候选和原始清单。
- `verify(input, candidate, draft)`：独立重新打开候选，返回功能读回、差异白名单、校验结果和证据等级。
- `rollback(source, historical, options, outputStage)`：按机型版本策略恢复历史内容并生成新候选。
- `outputFilename()`：返回机型要求的官方更新文件名。

协议响应使用带版本号的 JSON schema。未知 schema、字段类型错误、非有限数、路径逃逸、符号链接或适配器进程异常都必须失败关闭。

## 5. 数据模型与存储

项目不再以固件 SHA 单独作为草稿身份。一个输入固件可以创建多个独立编辑项目。

```text
data/
  objects/<sha256>.bin
  projects/<project-id>/project.json
  projects/<project-id>/assets/<asset-id>
  builds/<build-id>/firmware.bin
  builds/<build-id>/manifest.json
  ledger.jsonl
  settings.json
```

`project.json` 保存 `adapter_id`、适配器 schema、输入 SHA、标题、裁切草稿、关机图案草稿和最近构建引用。任何固件偏移、编译地址或校验字都不得由浏览器提交；这些值只能来自适配器代码和输入证据。

`manifest.json` 至少包含：输入与输出哈希、机型、适配器版本、版本策略、父构建、功能配方、目标逻辑差异、容器差异、校验结果、工具链身份、源码来源、验证等级和 `hardware: not_tested`。

## 6. 备份与恢复

平台明确区分两种备份：

- **官方包备份**：包含用户导入的官方 BIN、身份信息、清单和恢复说明；只能恢复电脑端输入对象，不能声称恢复相机 Flash。
- **编辑项目备份**：包含项目 JSON、图片素材及其哈希，不包含固件 BIN；恢复时必须先存在 SHA-256 完全一致的输入。

两类备份采用不同 kind 和 schema，导入时不得互相降级解析。恢复使用完整暂存、成员白名单、大小限制、哈希验证、文件同步和目录原子发布。备份不能携带绝对路径、候选固件路径或相机恢复声明。

## 7. GR III 适配器

### 7.1 身份与版本

首个支持基线固定为当前提供的 `fwdc239b.bin`：项目 588、14 个已验证分区、内部版本 `2.10.21.27`。输出继承输入版本，外层两个版本字段、RTOS 版本和 CPU 版本必须与输入一致。GR III 构建、历史载入和回退都不得自动提升版本。

当前反汇编证据表明严格较低版本会被拒绝，而相等值通过已定位的比较分支；这不是完整相机验收证明，因此构建清单仍标记硬件未测试。

### 7.2 关机图案

适配器从 GR III `RES` 读取五个已识别的 720×480 JPEG 资源及其真实记录。UI 支持导入 PNG、JPEG、WebP、BMP、TIFF，提供完整显示和铺满画面两种模式、命名、排序和删除。

实现分为两个内部层次，但交付为同一功能：

1. 先建立五个原生槽位的可靠替换、编码约束、资源回读和非目标资源保持。
2. 再完成类似 GR IV 的自定义条目注册表、菜单选择和持久化补丁，最多管理 16 个自定义图案。

新增菜单能力必须以 GR III 的选择表、描述符、资源消费者、设置保存和恢复路径为依据。不得复用 GR IV 的选择 ID、内存地址或代码洞。

### 7.3 裁切比例

原厂 `3:2` 与 `1:1` 保持只读。自定义比例支持命名、预览、排序与删除。

实现必须从已经定位的 `StillAspectRatio` 读写处理器继续追踪菜单、设置持久化、拍摄几何、JPEG、DNG/RAW 和回放消费者。GR III 专属原生补丁使用 ARM 指令边界、预期原字节、明确代码空间和可恢复注册表；任何调用链未闭合时，相应构建必须返回具体阻断项，而不是猜用 GR IV 补丁。

构建后的验证器重新读取裁切注册表、身份、顺序和几何，并确认所有非目标程序字节不变。

### 7.4 容器与校验

构建沿用已验证的帧重放模型：未改变的帧原样复用，目标帧重新编码。根据实际修改修复 CPU 大端加和、解码区小端加和和外层容器加和；版本不变时不得写版本字段。无修改构建必须逐字节等于官方输入。

## 8. GR IV 适配器

GR IV 以 `gr-custom-tool` 当前公开版为行为基准，保留其精确官方 `1.11.10.7` 布局、canonical-base 恢复、裁切注册表、关机菜单、ICON 资源、LLVM 编译链和独立读回语义。

GR IV 版本策略保持参考实现：官方 `.7` 的首次构建最低为 `.10`，后续使用输入、导入记录和本地构建历史中的最高同家族尾号加一；拒绝占用、低于建议、跨家族和超过 255 的版本。回退固件恢复历史内容，但生成一个更高的可接受版本，而不是直接降低版本号。

没有用户提供的 GR IV 官方 BIN 时，自动验收限于：参考源码迁移完整、原测试保持通过、桥接 schema 测试通过和已知常量一致。UI 与清单标记 `reference_verified`，不得显示为本机样本或硬件验证。用户后续导入与参考适配器严格匹配的 GR IV 文件后，才运行完整文件级构建与回读。

## 9. 共享编辑体验

导入后页面顶部显示机型、输入版本、适配器、完整 SHA-256 和证据等级。左侧只显示该适配器声明支持的功能；同一套裁切与关机编辑器消费标准化草稿，不直接理解固件布局。

用户修改草稿后先保存，再通过风险确认生成。生成结果提供固件、构建清单、输入/输出哈希和验证摘要。历史页面按机型和适配器隔离展示，允许下载仍存在的固件、载入为新草稿或生成回退候选。

GR III 页面不显示可编辑版本输入。GR IV 页面显示参考实现的建议版本和合法手动版本输入。GR II 在没有适配器时只显示“不支持”，不出现编辑或构建按钮。

## 10. 构建事务与错误处理

平台创建同一数据卷上的私有暂存目录，向适配器传入只读输入路径和唯一输出目录。适配器完成构建后，平台依次执行：

1. 检查输出文件名、类型、大小和暂存目录边界。
2. 调用独立验证器。
3. 生成平台规范化清单并与适配器报告交叉核对。
4. 同步固件、清单和暂存目录。
5. 以不覆盖现有构建的原子发布注册到 ledger。

任何阶段失败都删除仅由本次事务拥有的暂存内容，不改变输入、草稿、历史和已有构建。适配器超时、退出码异常、非 JSON 输出或报告与成品不一致都视为失败。

## 11. 验证策略

所有行为变更遵循测试先行。

### 11.1 共享平台

- 适配器唯一检测、未知固件拒绝和跨机型项目拒绝。
- 项目与素材 schema、备份往返、恶意 ZIP、路径逃逸和符号链接。
- 构建中断、验证失败、重复发布和 ledger 原子性。
- GR III/GR IV 版本策略完全隔离。
- HTTP 令牌、同源、上传限制、下载白名单和静态路径边界。
- 关键桌面与窄屏浏览器流程的真实渲染检查。

### 11.2 GR III

- 官方输入精确身份和 14 分区解析。
- 无修改构建逐字节一致。
- 关机资源编码、定长/布局、五槽回读、多条目注册表和非目标资源保持。
- 自定义裁切的编译、指令预期值、注册表、原生读回、JPEG/DNG 相关数据路径差异白名单。
- 四处版本保持不变和所有已知校验层。
- 对任意额外逻辑字节、版本变化、损坏帧或校验破坏失败关闭。

### 11.3 GR IV

- 运行 `gr-custom-tool` 现有测试作为参考回归。
- 为 JSON 桥接增加同值输入/输出、异常、超时和路径边界测试。
- 对裁切、关机菜单、版本分配、canonical-base、历史与回退做跨接口契约测试。
- 没有真实 BIN 时明确跳过样本级测试并报告原因，不把跳过记为通过。

## 12. 交付顺序

实施按以下依赖顺序进行，但最终目标是同一平台完整交付：

1. 抽取共享领域模型、适配器协议、机型检测和隔离存储。
2. 接入 GR IV Python 适配器并迁移参考功能与 UI 契约。
3. 把现有 GR III 解析、备份和候选验证迁入 GR III 适配器。
4. 完成 GR III 关机图案生成与独立回读。
5. 完成 GR III 自定义关机菜单和裁切原生补丁。
6. 接入共享历史、回退、编辑备份、构建下载和清单。
7. 完成全量自动测试、浏览器验证和离线成品审查。

每一步都必须保持已经完成的适配器测试通过，不能为了推进 GR III 而降低 GR IV 的原有校验，也不能用 GR IV 的测试替代 GR III 证据。

## 13. 完成标准

满足以下条件才称为软件实现完成：

- 同一 UI 能正确识别并隔离 GR III 与 GR IV 项目。
- 两个机型都具备裁切、关机图案、草稿、编辑备份、构建、清单、历史、载入和回退入口。
- GR III 从精确官方输入生成同版本候选；GR IV 使用参考版本分配规则。
- 每个候选由对应独立验证器重新打开，功能读回与差异白名单通过。
- 生成与下载只暴露完整发布的候选，不暴露暂存或失败文件。
- GR IV 无样本时准确标记参考验证限制；GR III 准确标记硬件尚未测试。
- README、使用指南、许可证与第三方说明和实际行为一致。

完成标准不包含滤镜、GR II 实现、自动写卡、自动刷机、硬件成功保证或变砖恢复保证。
