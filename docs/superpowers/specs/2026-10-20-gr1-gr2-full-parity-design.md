# GR / GR II 全功能对齐设计

状态：2026-10-20 用户已确认方案和计划，授权当前会话直接实施，先 GR II 再 GR；不重复请求常规确认。实施进度见配套计划及功能对照清单。

## 目标与验收原则

把 GR3、GR4 当前 M10V 固件功能和网页操作移植到 GR 5.01、GR II 3.00。项目内部 ID 使用 `gr1`、`gr2`；GR 指 2013 年数码 GR，不是胶片 GR1 或 GR DIGITAL。功能目标为逐项完整对齐。只有以机型官方指令、硬件资源或运行时实验证明无法实现的项目才能豁免；尚未定位接口、校验未解、实现困难、性能未测均不构成豁免。

“功能和操作对齐”与“不同传感器输出像素完全相同”分别验收。后者不能靠共用算法证明；需要同场景实拍与原厂基底/色彩管线校准。未连接相机时，交付明确标为离线候选，不宣称完成启动、刷入或成像验收。

## 路线选择

采用已认可的方案：共享 UI/胶卷语义/纯算法，独立机型 ABI、资源与封装。先建立 GR/GR II 共通的 UNITY 基础，再完成 GR II 端到端链路，然后用相同验收要求推进 GR。GR 的容器、资源与头识别研究可以先行，运行体地址不能继承 GR II。

没有选择整套复制 GR3，是因为小端代码、地址和对象布局不同；没有选择仅开放资源替换，是因为不能满足完整固件与操作目标。参考项目只提供需本地验证的线索。

## 模块与契约

1. `node/unity-firmware.mjs` 拥有通用 UNITY 严格解析与无修改编码逻辑；`node/gr1-firmware.mjs`、现有 `node/gr2-firmware.mjs` 只使用各自精确 profile。保留原 GR2 导出 API，避免调用方被迁移破坏。
2. `node/unity-model-profiles.mjs` 保存官方大小/完整 SHA、组件 SHA、版本、目录偏移和记录数；不按文件名选择机型。资源数据与未知尾部保持原样，边界/重叠/名字错误即拒绝。
3. `scripts/analyze_unity_update.py`、`scripts/analyze_unity_runtime.py` 输出按机型锁定的证据；从原厂调用链证明校验、文件位置→运行地址、内存/文件/时钟/菜单/拍摄接口。候选地址不能进入可写 profile。
4. `native/gr1/`、`native/gr2/` 独立管理入口、对象偏移、字节序、链接布局和原指令 preimage。现有共享胶卷算法和协议只复用明确不含 GR3 地址的部分；大端目标构建须证明没有不支持的浮点或编译器辅助调用。
5. `node/adapters/gr1/index.mjs`、`node/adapters/gr2/index.mjs` 提供独立机型入口；构建接口与取消/来源绑定遵循现有 adapter 机制。`/gr1/`、`/gr2/` 共用 GR3/GR4 实际工作台操作与设计系统，并由能力控制可构建项。
6. 能力状态使用 `researching / verified_offline / hardware_verified / proven_unavailable`，同时给出 `can_read`、`can_build`、证据位置和原因。未知功能可以查看目标说明，但不得把无效选项保存成成功固件；导出仅允许已经完成离线构建与独立回读的组合。

## 更新与构建

先证明 `nUpdateCsum` 的算法、覆盖范围、初始化/收尾、尾部处理以及实际比较路径；分别用 GR/GR II 两组件原厂值、变异数据、分块边界和原厂 CPU 执行交叉验证。不关闭 bExecVerify/bCompareCsum 来代替校验重算。先前文档中的“updater”称呼不能代替组件真实角色与启动链证明。

加载记录的 source/address/length/aux 字段必须沿启动拷贝/清零代码验证。禁止把零填充区或 aux 区猜作注入空间。运行体扩展需要证明被加载、地址不冲突、分支可达、栈/ABI 正确，且不干扰更新与恢复入口。

构建链路：来源身份→解码与校验→语义配置→机型 ABI 转换→大端原生编译→每处原像核验→资源/代码修改→校验重算→嵌套重封装→独立解析/回读→产物与审计摘要。任一步失败不留下可下载的最终文件。下载名由机型更新流程证明，不从 GR3 名称推断。

## 机内运行与性能

菜单需独立确认所有权、构造析构、按键分发、中文字体和图标格式；分配失败、取消、返回原菜单走原厂安全路径。持久化保留现有语义，序列化不得依赖本机端序或 C 结构体 padding。

静态 JPEG 接入需证明原厂 profile、Y/C 或 RGB 格式、分辨率/stride、缓存、内存所有权、RAW/预览关系、拍摄模式和取消/失败生命周期。RAW CFA 保持原始内容。取景与机内 RAW 再开发按当前 GR3/GR4 实现范围对齐，不额外承诺实时胶卷效果。

先测内存与各算法的 CPU 成本，再决定大端 SIMD/整数实现或等价优化；不能通过默认关闭质感效果宣布完成。若某组合受硬上限限制，保留具体分辨率、模式、耗时/内存证据及替代实现调查结果后再申请功能豁免。

## 验证与交付门槛

- 官方样本缺失时显式报告；本次两个根目录输入存在，相关集成测试不得因旧路径而跳过。
- 格式与 CPU：两机型独立样本、损坏/截断/错机型/未知版本、原样往返、修改校验、原厂指令执行、寄存器/栈与保护区。
- 构建：最小变更及所有开放功能组合；最终 `.frm` 独立解包回读；未修改组件、RAW 区域、更新恢复路径符合审计约束。
- 页面：两机型从导入到下载/SD 导出的实际 HTTP 与浏览器操作；错机型拒绝、来源切换、草稿隔离、撤销重做、预检过期、取消与保存确认。
- 真机：原厂对照、刷入/恢复、冷启动、全部菜单、JPEG/RAW+JPEG、连拍/取消/低存储、断电参数恢复、SD 故障、时间/方向、图片与色彩。没有设备验证时保留待验收标签。
- 对照清单每项须有实现文件、固件证据、自动检查、浏览器记录及真机状态；豁免另给底层证据。清单未闭环时不宣称 100% 完成。
