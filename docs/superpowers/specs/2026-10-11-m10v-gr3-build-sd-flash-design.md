# m10v GR III 固件候选与 SD 卡更新设计

状态：用户于 2026-10-11 确认。本文扩展 [原本只读的本地工作台设计](2026-10-10-m10v-gr3-web-design.md)；已实现的导入、电脑备份与恢复演练继续保留。用户选择以相机官方 SD 卡更新入口刷写，且目前只有一台 GR III Street Edition 2.10，没有经验证的救援工具或测试机。

## 目标与验收语义

目标是让仅用 Node.js 运行的本机 Web 平台完成精确官方包分析、最小修改候选构建、独立回读校验、SD 卡准备与写后校验。相机更新菜单仍由用户操作；网页不宣称存在已验证的 GR III 远程写入协议，也不把“文件已写入 SD 卡”称为“相机刷写成功”。

“完整固件分析”在本阶段指针对所需操作闭合证据链：容器和 14 个分区、所有候选差异、对应的版本与完整性检查、更新状态和关机资源消费路径。它不意味着逐条解释整个 RTOS、Linux 和全部程序的每条机器指令。每个尚未闭合的调用链都明确阻断相应能力。

首个修改目标限定为 Street Edition 的 `RES/B:\\Resource\\Jpeg\\Collabo.jpg`。自定义裁切保留独立研究门禁；在菜单、预览、JPEG、DNG/RAW、回放及持久化路径未贯通前，不进入刷写候选。版本递增只作为同版本更新被实证拒绝后的备选，不自动启用。

## 已有证据及关键假设

- 唯一基线为 `fwdc239b.bin`，30,391,780 字节，SHA-256 `d6a3c9c288d784080e7b283222ecdd8752adfeed6faa36dab44f73115354bfd4`，项目号 588，内部版本 `2.10.21.27`。机身公开显示 2.10；机身内部尾号尚未独立读取。
- 已定位按类型分支的多个拒低版本 `BLO`、上层失败跳转、CPU 大端加和、解码区与外层容器的小端加和。仅改待刷包中的 `BLO` 不会改变机身当前更新器的本次验收。
- 原包无改动重封装可逐字节复现。内存中的单字节资源变动与四处版本递增试验可独立重解码并修复已知加和；尚未证明真实 JPEG、相机容量、其它验收或启动结果。
- 官方资源的静态选择值 1 对应 `Collabo.jpg`，照片显示另有 `Today` 叠加。机身持久化选择值及资源替换后的完整显示链仍未证明。
- 电脑备份 ZIP 包含官方安装包，不包含相机内部闪存镜像，也不能作为变砖恢复证明。

## 选择的实施路线

考虑过三种路线：立即输出并写卡修改包；从网页直接向相机传输更新；本机生成与校验候选、由 SD 卡进入官方更新菜单。第一种在唯一机身上缺少故障恢复证据；第二种没有已验证协议。采用第三种，并分别给官方包与修改候选设能力门禁。

### 1. 固件分析与候选构建

Node 后端以原包完整哈希和严格解析为入口。构建器仅接受白名单中的 `Collabo.jpg` 替换请求；验证输入 JPEG 完整性、720×480 尺寸、相机所需的编码特征和资源长度/布局边界。任何一项特征没有从官方样本与消费者代码得到足够依据时，构建返回具体阻断项，不输出候选。

构建阶段从不可变官方基线生成目标解码区，记录每一处变化的分区、逻辑偏移、预期原字节和目标字节。只修复已证明的校验字，再按原帧边界重编码；无改动重建必须与官方原包完全相同。不同于构建器的严格解析器从成品重新解码，核对每个分区、资源记录、版本字段、所有已知校验和以及非目标区域逐字节不变。报告包含输入/输出哈希、长度、差异白名单、帧变化、校验与剩余未验证项。构建失败时不得在下载、备份或 SD 写卡目录留下半成品。

候选先留在隔离诊断区，不通过 HTTP 下载路由、静态目录或备份 ZIP 暴露为可刷写文件。已知算术校验通过只是 `offline_verified`，不是 `camera_verified`。

### 2. 版本策略

默认沿用 `2.10.21.27`，以同一代码基线制作单功能候选。公开 2.10 不能证明机身内部尾号相同，也不能证明整条更新链接受同版本。只有记录了相机明确的拒绝阶段及内部版本证据，才进入递增版本研究；四处版本字段、CPU `0x7C` 大端补数、解码区与容器加和须同步且独立回读。不得通过更改分区类型、填 `0xFFFFFFFF` 校验哨兵或补丁待刷 RTOS 的 `BLO` 来规避本次门禁。

### 3. SD 卡准备及相机执行

官方原包可进入写卡流程：前端展示精确文件身份、目标卡和将写入的文件名；后端仅接受明确选中的可移动 SD 卷，拒绝系统盘、符号链接、路径越界和已有同名文件的静默覆盖。写入采用目标卷上的临时文件、文件及目录同步、原子改名，然后从目标卷重读并比对 SHA-256 与字节数；任何失败都报告“不具备更新条件”。没有经实物卡验证时，状态为 `sd_write_untested`。

修改候选的 SD 写卡、下载和备份导出须由服务端能力检查统一控制。在本机仅有唯一相机且没有已验证救援路径的现状下，保持关闭，页面显示准确的阻断原因。前端按钮、HTTP 直接请求和本地候选文件路径都不能绕过。官方包写卡成功后，Web 只提供理光官方更新步骤与人工结果记录；不通过软件自动触发相机更新，也不宣称相机已更新。

## 状态及记录

`official_sd_ready`、`candidate_offline_verified`、`candidate_sd_blocked`、`camera_update_in_progress`、`camera_verified` 是不同状态。后两者只能依据人工/设备验证记录推进，不能由离线测试或 SD 回读自动得出。每次分析、构建、写卡尝试都保存输入哈希、操作参数、校验结论与失败阶段；不保存敏感设备序列号。候选构建与 SD 写卡的错误均不得改变原厂备份。

## 界面与错误处理

在现有页面增加“候选审查”和“SD 卡准备”区，先给用户渲染预览确认。每一步展示实际可执行动作、文件哈希、目标卷、能力状态和未满足条件。遇到无卡、只读卡、容量不足、写后哈希不符、候选完整性失败或硬件恢复未验证时，停在明确的失败状态；不显示可点击的修改版写卡动作。

## 验证顺序

1. 构建器的无改动输出与官方原包 SHA-256 完全一致；输入只改目标资源时，输出的逻辑差异限制在该记录与已声明校验字。
2. 使用独立解码与变造样本验证版本、JPEG、资源表、分区、帧和各级加和拒绝逻辑；先用内存/临时卷模拟写卡失败、部分写入与哈希不符。
3. 在真实 SD 卡上验证官方原包写入与拔插后重读，确认卷识别、原子写入、文件名和哈希。此步骤不要求把官方包刷进相机。
4. 修改版候选仍不能写卡，直到更新状态链、真实图片兼容性、机身内部版本与可执行的机身恢复路径得到可审查证据。首次实机更新需要独立的受控测试与结果记录。

## 交付边界

本阶段可交付实际工作的**官方固件 SD 卡准备功能**与**修改候选离线构建/审查能力**。在唯一机身、无救援工具的条件下，不交付“修改版一键刷机成功”的承诺；修改版的相机端刷写能力仍受独立硬件验证门禁约束。理光官方更新程序对修改包的接受情况只能通过受控实机验证确定。
