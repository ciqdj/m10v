# GR III / GR IIIx 功能统一设计草案

状态：用户已确认“同步一下，要求一模一样”；正在实施与离线验证。

## 目标与基线

用户要求两款机型功能保持一致。以已 fetch 的 origin/main `aa9207f7cd55cb9d704a0beba7a5ec75097daf2c` 为本次源码审计基线。未读取生产服务器，不将此提交称为当前线上提交。

功能、菜单、配置和成像策略共用；机型身份、官方输入、CPU、镜头参数和升级兼容分别适配。不得通过减少 GR III 功能来实现一致。

## 底层复用依据与边界

现有 docs/research/gr3x-native-parity.md 记录：锁定的 GR III 2.10 与 IIIx 1.60 官方 RTOS 同为 17,520,064 字节，差异仅 31 字节、19 个对齐字。node/gr3x-native-port.mjs 在每次移植时重新核验差异数量、拒绝覆盖机型专属字，并独立回读输出全部分区。

这为复用 RTOS 功能提供强依据，不能据此推断不同镜头、CPU 和实机时序必然等价。首次审计时工作树缺少 bin/ 官方输入；执行阶段已恢复本机精确官方输入，并分别构建与独立回读两款候选。

## 方案与建议

建议沿用已有差分移植：同一套功能配置构建经过审计的公共 RTOS，再移植到各自官方包，保留 IIIx 全部 CPU、身份和受保护字。新增共享能力定义供网页、预检和构建使用，防止各处重复写 model===gr3 导致后续分裂。

另两种方案不采用：逐功能复制一套 IIIx 实现会持续产生漂移；直接共用同一个 BIN 会破坏机型身份和 CPU 边界。用户已确认按统一方案执行。

## 实施契约

1. 先统一 ISP 成片、原生预览、颗粒和新增胶卷，再统一槽位、HDF、光晕及网页入口，最后核对镜头相关裁切和开关机资源。
2. 公共功能默认与可选范围一致；出现不能支持的项目，必须有底层差异证据和明确原因，不能将历史门禁当作永久限制。
3. 自定义焦距使用机型镜头基准：III 为 28mm，IIIx 为 40mm；IIIx 裁切比例、原厂两档默认值、图标及元数据须先核实，不能照抄 III 的 28–100mm 合同。
4. 保存现有存档迁移、槽位独立性、目录 ID、RAW 保护、每张快照与成像生命周期。普通胶卷关闭空间效果时，编码桥保持零像素工作；IIIx 不得继续以 CPU LUT 作为达到功能一致的捷径。
5. 新增功能和修复须同时检查 III/IIIx 消费者；仅硬件与升级适配允许分支。GR IV 不纳入本次功能对齐。

## 验收与交付

- 建立两款机型的配置/能力对照检查，覆盖十位置、新胶卷、颗粒、HDF、通用光晕和机型切换；保留错误输入和冲突检查。
- 分别执行构建、官方哈希与 preimage 核验、预算检查、最终 BIN 全分区回读、CPU/身份/19 字保护，以及 ISP 真实任务投递和关闭效果的零像素工作检查。
- 分别交付可识别的候选、receipt、manifest、SHA256 和设备清单。两款机型各自验证菜单、预览、首张、连拍、JPEG/RAW、回放、存档与重启。
- 离线通过不代表 IIIx 设备通过；依照现有发布流程，在对应候选用户验收后再合并、推送和部署。
